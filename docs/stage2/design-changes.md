# Stage 2 design changes

Every difference between the Stage 1 design (tag `stage1-submitted`) and the implementation,
recorded when it is made.

| # | Date | Original design | Implemented change | Reason | Impact (features, use cases, classes, patterns) |
|---|---|---|---|---|---|
| 1 | 2026-10-20 | Scenario CSV format has a separate cash deposit/withdrawal direction column (Stage 1 report, F01 input) | Cash direction is encoded by the counter account `CASH`: a deposit is CASH to customer, a withdrawal is customer to CASH | The rules already read sender and receiver; a second field saying the same thing could disagree with them | F01 (`ScenarioCsvFormat`), F02 (R1, R3 read `Transaction.isCashDeposit()`); no pattern change |
| 2 | 2026-10-20 | `Account` has `id`, `bankId`, `watchlisted` | `Account` has `id`, `watchlisted` | No feature reads the bank code, and carrying it would add bank fields to every format and to `Transaction` | None beyond `Account` (not on the UMLet class diagram) |
| 3 | 2026-10-20 | Every account in the data is stored and monitored | Parties outside the bank (the `CASH` counter and ids starting `EXT-`) appear in transactions but are not stored as accounts or monitored | A bank monitors its own customers; without this, a foreign sender of a planted wire received its own threshold report. IBM data has no `EXT-` ids, so all its accounts stay monitored | F01 (account creation, import summary), F02 (accounts scanned); `Transaction.isOutsideBank()` added; no pattern change |
| 4 | 2026-10-20 | `WindowedRule.isMatch(window: List<Transaction>)` | `isMatch(account: Account, window: List<Transaction>)` | R2 and R4 must tell money in from money out, which depends on which account is being scanned | F02; `WindowedRule` and all six rules; Template Method unchanged (`evaluate()` still fixes the algorithm). The class diagram is updated in Stage 2 |
| 5 | 2026-10-20 | `RiskScorer.score(match, account)` | `score(match, account, rulesTriggered)` | The score includes how many different rules the account triggered (Stage 1, F02 step 5), which one match cannot know | F02; `RiskScorer`, `MonitoringService` |
| 6 | 2026-10-20 | `AnthropicLLMClient(config: ModelConfig)` | `AnthropicLLMClient(config: ModelConfig, apiKey: String)`; the key is read from `.env` by `EnvFile` and never stored in `ModelConfig` | `ModelConfig` is shown in logs and reports (model name, prices); keeping the key out of it means it cannot leak through them | F03, F10, F11 (LLM access); Adapter pattern unchanged |
| 7 | 2026-10-20 | `RetryingLLMClient` retries failed calls; the design does not say which failures count | New `LLMException(retryable)` in `tracewise.llm`. `LangChain4jClient` turns LangChain4j's `RetriableException` (rate limit, timeout, server error) into a retryable one and every other LangChain4j failure into a non-retryable one; `RetryingLLMClient` retries only retryable failures (2 retries, waiting 2 s then 4 s) | Retrying a bad API key or invalid request cannot succeed and only delays the error; decorators must not see LangChain4j types, so the replay client and future providers use the same exception | F03, F07, F10, F11 (LLM failures); Decorator and Adapter patterns unchanged |
| 8 | 2026-10-20 | `LLMClientFactory.create(config)`; the design names no constructor and no setting that selects `ReplayLLMClient` | `LLMClientFactory(apiKey, replayStore)`; `ModelConfig.provider` is `anthropic` or `replay`. `ReplayStore` keeps one JSON file per request, named by the SHA-256 of the request | The key stays out of `ModelConfig` (change 6), so the factory receives it separately; replay is chosen the same way as any provider, so tests and demos switch with configuration only | F03, F07, F10, F11; Decorator (recording outside retrying) and Factory-built stacks as designed |
| 9 | 2026-10-20 | `TraceStep(turn, toolName, arguments, result, durationMs)`, `AgentOutcome(status, finalText)`, `AgentTask` with three methods, `AgentTrace` with no constructor given, `AgentLimits.maxCostCad` with no default | `TraceStep` and `AgentOutcome` also carry `subject` (the alert or question being worked on), and `TraceStep` carries `error`. `AgentTask` adds `outputProblem(finalText)` (default: none). `AgentTrace(subject, pricing: ModelConfig, cadPerUsd)` plus `addUsage`, `steps`, `usage`, `outcome`. `AgentLimits.DEFAULT` is 12 turns and CAD 1.00 | `AuditLog` is one shared listener, so each event must say which alert it belongs to; the error flag lets the step panel and audit show failed calls. The runner needs the task's format check to ask once for a correction (F03 error case). Cost in CAD needs the model's USD prices and a rate. A 12-turn Sonnet run costs about CAD 0.20, so CAD 1.00 stops runaway runs only | F03, F07, F08, F10; Observer (`AgentTrace` subject, `AuditLog` listener) as designed |
| 10 | 2026-10-20 | `ClaimVerifier.verify(claims: List<Claim>)`; `ClaimCheck(confirmed, reason)` linked to one `Claim`; F05 also says each total must equal the sum of the transactions it cites, but no class models a total | `verify(claims, totals: List<TotalClaim>)`; new `TotalClaim(description, amountCad, transactionIds)` in `tracewise.agent`; `ClaimCheck(claim, confirmed, reason)` names its claim in words; `VerificationStatus` is VERIFIED, PARTIALLY_VERIFIED or UNSUPPORTED (no claims); `VerificationReport.summary()` gives the banner text. Dates are compared in UTC | Implements the totals check that F05 promises; one check type for both kinds of claim keeps the report a single list for the GUI, CLI and F12 counts | F05, F03, F10, F11, F12; no pattern change |
| 11 | 2026-10-20 | `InvestigationTask.parseFinding(text)`; `AgentFinding` holds verdict, confidence, indicators, narrative, claims and its `AgentTrace` | `parseFinding(text, trace)`; `AgentFinding` also holds `totals` (change 10) and `incomplete`, which is read from the trace's outcome | The runner's outcome, not the text, says whether a limit cut the run short | F03, F05; no pattern change |
| 12 | 2026-10-20 | `Case` aggregates `Alert` objects; `CaseRepository` and `AlertRepository` as listed; `InvestigationResult(status)` with an optional finding; `InvestigationService` depends on `AgentRunner` | `Case` keeps alert ids; a case created by an investigation gets the alert's number (`ALR-00007` opens `CAS-00007`). Findings are stored as one JSON document each, with their trace, verification and pricing. `AlertRepository.updateStatus(id, status)` added (NEW to IN_CASE). `InvestigationResult(caseId, status, finding, trace, message)`. `InvestigationService` receives the runner through a `Supplier`, so commands that never call the model run without an API key | Alerts are already stored; a case needs only their ids. Deterministic case ids keep replayed demos identical. One document per finding keeps the nested claims, checks and steps readable without many tables. The result carries the trace and the reason for failure that the GUI and CLI show | F03, F08; State (case transitions) and Observer as designed |
| 13 | 2026-10-20 | `AppConfig(databasePath, userName, userRole)` chooses provider and model (key decision 6), details not given | `AppConfig` adds `model: ModelConfig`, `replayDir`, `envFile`. CLI root options `--llm anthropic or replay`, `--model`, `--record`, `--replays` (or `TRACEWISE_LLM`, `TRACEWISE_MODEL`, `TRACEWISE_RECORD`, `TRACEWISE_HOME`). `ModelConfig.of(provider, model, record)` takes prices from a table of verified models (Haiku 5.5, Sonnet 5.5) and rejects unknown ones | Cost must be reported per run, so a model without known prices is refused rather than shown as free; the launcher sets `TRACEWISE_HOME` so `.env` and recordings are found from any folder | F03, F07, F10, F11; Factory Method (`LLMClientFactory`) unchanged |
| 14 | 2026-10-20 | `AgentLimits(maxTurns, maxCostCad)`; no limit on tool calls in one model response | `AgentRunner` runs at most 10 tool calls per response; the rest get an error result without running | Found in code review: one response could otherwise ask for any number of tool runs, outside the turn and cost limits | F03, F07, F10; no pattern change |
| 15 | 2026-10-20 | `ActionCommand(validate, execute, describe, targetCaseId)`; `LinkAlertsCommand(alertIds)`; `ApprovalRepository(save, findById)`; `PendingAction.markExpired()`; `CommandContext` includes `memory()` | `ActionCommand` adds `target()` (the alert, account or case named in the audit entry). `LinkAlertsCommand(caseId, alertIds)` names the case the alerts join. `ApprovalRepository` adds `findPending()` and `nextId()` (ids `APR-00001`). `PendingAction` also keeps the reviewer, decision reason and time; `markExpired(reason)` records what changed. Proposals store their command as JSON with its type, so they survive a restart. `CommandContext` has no `memory()` until F04 builds case memory. `Actor.isHuman()` and `Actor.AGENT` added; `IllegalTransitionException` is an `IllegalStateException` | The audit trail must say what each action touched, including alerts and accounts that are not cases. The CLI exits between a proposal and its decision, so commands must be stored and rebuilt. Only analysts and supervisors may decide proposals | F06, F08; Command and State as designed |
| 16 | 2026-10-20 | `InvestigationTask(alert)`; `TraceWiseFacade.approve()`/`reject()` return nothing; `TraceWiseBootstrap` builds one object graph | `InvestigationTask(alert, caseId)`: the agent is told its case id, which the action tools need. The facade's `approve` and `reject` return the decided `PendingAction` so the CLI can show the outcome, including EXPIRED. `TraceWiseBootstrap.investigationTools(...)` is the one place the agent's tools are registered, and `create(config, llmSupplier)` lets tests record through the real wiring. `LinkedAlertsTool` (a read tool listed in the design) is built now so the agent can find alerts to link | Without the case id the agent cannot name the case it acts on. A test that wired its own tools drifted from the app and broke replay, so the tool list now has a single source | F03, F06; Factory Method (`ActionTool.createCommand`) as designed |
| 17 | 2026-10-20 | `PermissionPolicy.tierFor` with the approval-tier actions listed; action tools accept any target the model names | `PermissionPolicy` lists the actions the agent may take alone (priority, link, watchlist, task); every other action, including any added later, needs approval. New `ActionScope` (set by `InvestigationService` for each run) limits agent actions to the case under investigation and its alerts; `ActionTool` and `InvestigationService` take it. Linking into a case waiting for approval is refused, and a decided or expired proposal never leaves its case stuck in Pending Approval | Found in the second code review: after proposing a close, the agent could link more alerts that the approval would then close unseen, and a run on one alert could propose closing another case. A fail-safe default means a forgotten policy entry asks for approval instead of skipping it | F06; Command and Factory Method unchanged; the safety rule "the agent cannot close or escalate without approval" now also covers actions not yet written |
| 18 | 2026-10-20 | `InvestigationService` uses the runner, tools, verifier and case repository; `ApprovalRepository(save, findById, findPending, nextId)` | `InvestigationService` also uses `ApprovalQueue`: a run that ends without a finding (failed, cancelled, unusable answer) expires the proposals it made, and a new run on a case is told the earlier decisions on its proposals (status, reviewer, reason). `InvestigationTask(alert, caseId, earlierDecisions)`; `ApprovalQueue.forCase` and `expireUnfinished`; `ApprovalRepository.findAll` | A proposal whose evidence was never produced must not be approvable, and an agent that cannot see why it was rejected proposes the same thing again (both found in the F06 review) | F03, F06, F07 (triage re-runs cases); no pattern change |
| 19 | 2026-10-20 | `TriageReport(processed, failed, costCad)`; `TriageLimits` not drawn; "open alerts" not defined | `TriageLimits(maxAlerts, maxCostCad, filter)` with defaults 50 alerts and CAD 5.00. `TriageReport(endReason, items, costCad, durationMs, escalationsProposed, closesProposed, alertsLinked, otherActions)` with `processed()`, `failed()`, `failures()` and `summary()`; `EndReason` is COMPLETED, STOPPED, ALERT_LIMIT, COST_LIMIT or NOTHING_TO_TRIAGE. Triage takes NEW alerts plus alerts whose case is still open with no finding (an earlier run failed); investigated or decided alerts are skipped | F07 promises a summary of actions, proposals, failures with reasons, cost and time, and says a failed alert stays open for a later run | F07; no pattern change |
